01四层栈

上层是给 agent 读的「大脑」，下层是注入页面里跑的「引擎」。中间靠一个纯分发器连接。

读法：上面两层是「怎么写」，下面一层是「怎么渲」。中间那个 397 行的分发器是唯一把它们串起来的东西。

02四个核心设计决策

这四个决定解释了为什么它能做到「片子就是一个网页」，也解释了它的全部局限。

DECISION 01

工程就是一张 HTML，没有私有格式

三种标注让一张普通网页变成可编辑的片子：变量（可改的值）、data-om-id（可被指到的元素）、scene:id（分镜）。

好处是带走就能用，改道具不需要专有编辑器；代价是没有类型检查，全靠 om check 兜底。

the only source of truth
DECISION 02

不下载浏览器，直接说 CDP

在固定路径列表里找用户已装的 Chrome / Edge / Brave，找到后用 188 行的 cdp.js 直接对话。

不引入 Puppeteer，所以没有版本漂移；也意味着渲染完全依赖用户机器上的那个浏览器。

nothing is downloaded
DECISION 03

页面引擎与创作 API 分离

引擎只认时间（seek(t) / duration()），不关心你用什么方式画；创作 API 只提供积木（音效、配乐、拍点）。

这个分层让「按帧渲染」和「怎么写动画」彻底解耦，两套动画系统（手写 GSAP 与 clip grammar）才能并存。

DECISION 04

音轨从零合成，无采样无网络

约 1,800 行 DSP：乐器自己写，鼓组 8 套，音效 23 种。headless 浏览器加载页面读取场景标签和击打点，再在 Node 里合成整条音轨。

同一个源永远得到同一个文件——这是它能做「确定性交付」的关键。

no samples, no network, no dependencies

03渲染管线

一次 om render 背后发生了什么。要点是：一切并行，且任何异常都终止整次渲染。

关键：画面与音轨是两条并行的路，在 FFmpeg 处汇合。音轨不是后配的，是渲染流程的一部分。

04一条 capture 路径

这是整个框架最重要的架构约束——它解决了所有视频工具的通病：预览和成片不一致。

代价：所有能力都锁在浏览器上——没有 headless GPU 渲染加速，也做不了浏览器画不出来的东西（比如真人）。

05配乐合成

这是全仓库工程量最大、也最独特的部分：不调用任何音乐 API，从零合成。

设计哲学：音乐不是「配」上去的，是从片子的结构里长出来的——段落来自场景标签，落点来自切点。

06两套并存的动画系统

同一个框架里，手写 GSAP 和参数化 grammar 并行存在。它们解决的是两类不同的问题。

PATH A · 手写

GSAP timeline

作者直接写 gsap.timeline()，每个元素怎么动、什么时候动，全部显式控制。

适合：精品单条、需要独特表达的片子。代价：每条都要重写。

PATH B · 参数化

clip grammar

给一个 JSON spec（grammar 名 + 数据 + cues），grammar 自己算每一帧画什么。

适合：批量化、agent 生成、数据驱动的解说。代价：表达受限于 grammar 的设计。

08双层检查

check.js 的设计值得单独说——它让「每次改完都检查」从口号变成可承受的成本。

注意：还有渲后的 qa.js——它解码成片，量单帧闪烁、死时间、硬切、运动曲线。运动量低于 0.85 会直接判「像幻灯片」，我实测被这条逼着改了六轮。

09评论协议

「指着画面改」的底层是一个追加式 JSONL 日志。妙在它不绑定任何 agent。

11我们可以借鉴的三点

这三条与具体实现无关，是架构层面的判断。

01 · 渲染 / 静帧 / 预览 共用一条 capture 路径

这解决了所有视频框架的通病——预览和成片不一致。我们平台里预览页和最终渲染是两套代码，这是一个可以立刻借鉴的架构约束：让「看到的」和「交出去的」只有一条代码路径。

02 · 评论收件箱是模型无关的 JSONL 协议

我们现在用 Agent Key + 审批的思路是对的，但「指着画面改」这个交互（带时间点、元素、源码位置）比纯文本反馈精确得多。而且追加式日志 + 状态折叠的设计，天然解决了「状态和日志对不上」的问题。这个协议可以直接搬到我们的创作台上。

03 · 静态分析在前，采样在后

静态层毫秒级拦掉 80% 的错误，只有剩下的才开浏览器。这让「每次改完都检查」变得可承受——我们现在很多检查因为太慢，实际上没人跑。把检查按成本分层，是提高质量下限最便宜的办法。

一个反面的教训

om qa 会拿真实爆款的数据做基准，判「运动量低于 0.85 就是幻灯片」。这条逼我把片子从 0.14 改到 0.57——但最后一条始终没过。我的判断是：说明型片子本来就该慢读，硬加运动牺牲可读性。

这提示了一个通用问题：用数据基准做质检，一定会遇到「基准和意图冲突」的情况。框架应该允许带理由的豁免，而不是只有通过和不通过两态。
